## Remaining known limitations

- **Curriculum content does not publish on deploy, and the documented publish command is broken.** `pnpm import:content` has failed at module resolution since `915c7ca` (2026-07-31), when `src/usecases/ImportAmphContent.ts` was deleted out from under the script that imports it; `src/__tests__/scriptImportsResolve.test.ts` now pins it. `node scripts/seed-all-content.mjs` is the only script that writes lesson bodies and the quiz bank, and it is wired into neither `package.json` nor `vercel.json` (production deploy runs `prisma:deploy` and `db:seed:scenarios` only). So a merged lesson or quiz change reaches no learner until someone runs that seeder, and this repo keeps no record of when it last ran. Two consequences if you run it: it deletes and recreates each quiz's question rows, which can detach historical attempts from the questions they were graded against, and the lesson side is safe because lesson ids derive from module plus slug, not from content. Full table in `content/README.md`.
- **The glossary term popover is not wired into the lesson renderer.** `content/curriculum/glossary.json`, `src/lib/glossary.ts`, and `src/components/lesson/GlossaryTerm.tsx` all exist, but no file under `src/app/` renders them. `GlossaryTermButton` is imported by nothing outside its own module, `loadGlossaryManifest` and `lookupGlossaryTerm` are called only from `src/lib/__tests__/glossary.test.ts`, and the `data-amph-term` hook that `docs/stories/STORY-131.md` says the directive plugin emits appears nowhere in the code except that story file. So the popover never reaches a learner and the dead code is not a broken surface: learners read the inline parenthetical the author wrote, which is exactly the no-JavaScript fallback `STORY-131` describes. Two corrections to the record: the `#522` row above and `CHANGELOG.md:32` both describe the feature as shipped, and both say the manifest covers seven Module 0 terms when it now holds 31. Wiring it for real needs a term directive in the content plus an a11y pass over 31 new interactive controls, which is a product call rather than an incidental fix.
- **The early-bird discount has one mechanism, not the two the business doc once described.** `docs/business-layer.md` used to specify a cap by enrollment count ("Early 30 only"), while what exists applies a date window. As of this pass the doc describes the built mechanism. Whether a count cap is also wanted is Ryan's call, and `PricingTier` has no enrollment counter to hang it on. The same doc referenced a `PricingService` and `src/infra/pricing/` that were never extracted from the parent repo.
- **Two refund windows are live at the same time.** `src/usecases/RequestRefund.ts:7` enforces 7 days from `paymongoPaidAt` on the student side, while `src/domain/values/OrderRefund.ts` exports `REFUND_WINDOW_DAYS = 30` and the only consumer is `ProcessRefund.ts:87` on the admin side. A learner is told 7 days; the step that actually processes accepts 30. `docs/business-layer.md` now records both numbers instead of picking one. **Ryan to decide the policy.** _Resolved by PR #607: both paths now import `REFUND_WINDOW_DAYS = 7` from `src/domain/values/OrderRefund.ts`, with `REFUND_WINDOW_MS` derived from it. The student-side local constant is gone. `isWithinRefundWindow` is still bypassed by `RefundOverride`, by design._
- **A refund does not revoke access, and the code disagrees with itself about whether it should.** Neither `RefundOverride` nor `ProcessRefund` injects an enrollment repository, and `AuthorizeLessonAccess.ts:105` admits any enrollment whose status is `active`, which a refund leaves untouched, so a refunded student keeps studying until an admin separately cancels the enrollment through `AdminSetEnrollmentStatus`. Meanwhile the comment at `AuthorizeLessonAccess.ts:98` states that refunded enrollments are treated as not enrolled "intentional: a refund revokes access per the audit's P1-3", an assumption nothing in the refund path ever sets the data to satisfy. **Ryan to decide.** _Resolved by PR #608: both refund paths now call `revokeEnrollmentForRefund()` after a successful refund. The matching enrollment is moved to `cancelled` and audited as `enrollment.revoked_by_refund` (distinct from the existing `enrollment.revoked` used by `AdminSetEnrollmentStatus`).
