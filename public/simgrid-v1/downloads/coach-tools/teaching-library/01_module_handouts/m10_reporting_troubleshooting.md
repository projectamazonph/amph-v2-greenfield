# Module 10 Field Handout — Reporting & Troubleshooting

## The job

By the end of this module, you should be able to **Write plain-language reports and troubleshoot the five classic failure patterns.** The required practice handoff is **Account Audit + Report Builder** (`account-audit.html`), with a target of **75% simulator / 70% quiz**.

> **Operating rule:** A report earns trust when it links result, driver, action, guardrail, and checkpoint.

## What to look for

- **1.** Result versus target
- **2.** Primary driver supported by evidence
- **3.** Action and owner
- **4.** Guardrail and next checkpoint

## Worked thinking

“ACOS improved” is incomplete. A useful report states the baseline, the driver, the action taken, what must not worsen, and when the next review occurs.

## Practice before you open the simulator

Turn a set of metrics into a four-sentence report: result, driver, action, and checkpoint. Then diagnose whether the first issue is stock, price, reviews, competitors, or PPC.

## Decision standard

Fix the earliest confirmed failure in the customer path before treating downstream PPC symptoms.

## Key language

| Term                  | Plain-language meaning                                                 |
| --------------------- | ---------------------------------------------------------------------- |
| Driver                | The evidence-supported cause or contributor to a result.               |
| Guardrail             | The condition that prevents an action from creating unacceptable risk. |
| Checkpoint            | The agreed date or condition for review.                               |
| Troubleshooting order | Stock → price → reviews → competitors → PPC.                           |

## Exit ticket

Write one sentence for each prompt before moving on: What is the observed evidence? What is your smallest safe action? What guardrail or review date will tell you whether the action worked?
